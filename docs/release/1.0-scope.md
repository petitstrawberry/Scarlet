# 1.0 release scope and compatibility policy

Status: target policy for the coordinated release, not a statement that the
current trees meet it. RC1 remains blocked on the gates below. Read this with
the [roadmap](1.0-roadmap.md).

Current priority, updated 2026-09-06: the user deferred A618 work and confirmed
that the Boxcraft repair and its runtime verification are already complete.
ScarletUI and the separate `scarlet-sdk` tooling now have current-behavior
contracts. The SDK's unused partial `--offline` mode was removed with user
approval; its caches and project `--locked` behavior remain.
Do not reopen Boxcraft verification or start
A618 implementation/hardware work. Deferral does not certify A618 support or
silently remove it from the release scope; its disposition remains deferred.

The current-behavior [native API contract](1.0-native-api-contract.md) and
[ScarletUI application/extension contract](https://github.com/petitstrawberry/scarlet-ui/blob/main/docs/1.0-contract.md)
consolidate the native user-library and UI boundaries. Raw native operations
received the separately approved pre-1.0 unsafe correction and consumer adaptations.
Contract adoption is not release publication. The separate `scarlet-sdk`
repository defines its
[tooling contract](https://github.com/petitstrawberry/scarlet-sdk/blob/main/docs/1.0-contract.md):
CLI, schema-2 projects/bundles, static modules versus LSMs, sources/caches/locks,
image formats, matched Limine plugin, hooks, and runner behavior.
`--locked` is not a universal Cargo flag or network restriction.

The user selected documentation cleanup before final lock alignment. The
[kernel](../kernel/README.md), [userspace](../userspace/README.md),
[build](../build-system/README.md), [boot](../boot/limine.md), and
[memory](../architecture/memory-map.md) guides now describe the current source.
Published-source dependency selection, Nix/Cargo/project locks, and candidate
verification remain the final integration stage; local patches are not release inputs.

## What is being released

The first coordinated release covers Scarlet, SGFX, ScarletUI, scarlet-sdk, and the
Chromebook/Adreno integration. Align all **project-owned Cargo packages** in
the [inventory](1.0-packages.md), including applications, examples, fixtures,
tools, and BSPs, at `1.0.0-rc.1`, then `1.0.0`. Re-inventory at staging. Keep
vendored packages at their upstream versions and retain `publish = false`.
Version alignment is bookkeeping, not a claim that every example, device,
driver interface, or optional feature is a stable SDK.

Git distribution is sufficient. crates.io publication, a Vulkan frontend,
new backends, support for every Chromebook device, and completing all
experimental applications are not prerequisites. An experimental application
that is included in the chosen release image must still build: the label is
not permission to ship an unbuildable image. The existing full-image contents
are not reduced by this policy.

## Compatibility boundaries

| Boundary | Release compatibility contract | Not implied |
| --- | --- | --- |
| Application-facing native Rust APIs | Preserve supported public types, functions, traits, feature names, and documented behavior within a major version for the Scarlet native libraries and ScarletUI APIs. Additions must not break downstream code. | Stable Rust binary ABI, identical compiler internals, compatibility between arbitrary Git snapshots, or a blanket freeze of the SGFX implementation interfaces below. |
| scarlet-sdk build tooling | Preserve documented valid CLI and schema-2 project/bundle inputs and their meanings under the reviewed tooling contract. Ship the CLI and Limine plugin as a matched revision set. | Network isolation, propagation of every Cargo flag, a fully immutable `--locked` build, arbitrary plugin negotiation, or stability of internal helpers/cache encodings. |
| Scarlet native userspace ABI | Preserve released syscall numbers, argument/result meanings, and the layouts of supported ABI records on each supported architecture. Introduce a new versioned record or operation for an incompatible extension. | A binary for one architecture running on another, or every syscall being implemented in every kernel configuration. |
| Generic GPU ABI | Preserve existing versioned records and synchronous submit meanings. Add explicitly supported async submission with kernel-owned in-flight resources and read-only completion observation. Keep ABI versions independent of package versions. | Every execution dialect or GPU feature being supported, or submission/completion implying display presentation or CPU cache visibility. |
| SWS wire protocol | Ship and test a matched server/client/platform-adapter revision set. Keep optional operations capability-gated and preserve exact buffer generation/epoch/serial identity. | Compatibility with older independently installed clients. SWS remains an internal protocol under its existing policy; a package major number is not wire negotiation. |
| SGFX Rust implementation | Frontend, IR, backend/facade and codegen are updated and rebuilt as a compatible source set. Preserve consistent execution semantics, owned per-submission completion, ordered acceptance, bounded admission, resource retention and receipts for possibly accepted prefixes. The intended external application graphics boundary is the Vulkan C ABI. | A blanket 1.x Rust source freeze, an independently loaded SGFX Rust ABI, cross-queue synchronization, transactional failure, automatic device-loss recovery, or completion authorizing SWS/global buffer reuse. |
| ScarletUI | Preserve the supported application-facing view/state/layout/scene APIs, macros, and documented renderer/platform extension traits. | Pixel-identical rendering across hosts, a fixed frame rate, or an unconditional host-independent zero-allocation budget. |
| Kernel modules and board integration | Build and distribute external drivers/BSPs with the recorded kernel, toolchain, and project locks. Document the tested board and operations. | Stable Rust module ABI, arbitrary out-of-tree driver compatibility, or support for every device in the repository. |

The application-facing Rust compatibility rules follow the
[Cargo SemVer guidance](https://doc.rust-lang.org/cargo/reference/semver.html).
Treat externally reachable `pub` APIs as public by default except for the
explicit SGFX implementation boundary approved on 2026-09-06 below. This
exception covers SGFX's IR/traits, facade, backend/direct/codegen APIs and
exposed Rust dependency types; it does not waive native API or ScarletUI
application/extension contracts. Any further exception must be named in the
owning documentation and reviewed with its users. SGFX review concerns the
execution semantics and consistency of the selected source set.

The user approved including portable completion tracking and actual
asynchronous Scarlet GPU submission in 1.0; see the
[completion contract](https://github.com/petitstrawberry/sgfx/blob/90eb0641cf3dbdb415db6c48d81f7bf224d99984/docs/completion-contract.md).
The earlier [SGFX draft](https://github.com/petitstrawberry/sgfx/blob/90eb0641cf3dbdb415db6c48d81f7bf224d99984/docs/1.0-contract.md)
proposed freezing every Rust export. The policy below supersedes that proposal.
Other rendering, imported-image and presentation clauses still require review
before they become release guarantees. Contract definition takes priority over
expanding the verification baseline; tests must follow the selected guarantees.

[SGFX issue #1](https://github.com/petitstrawberry/sgfx/issues/1) places SGFX at
the common execution boundary between graphics frontends and complete backends.
ScarletUI can remain a direct IR frontend, while a future Vulkan frontend owns
its API-specific objects, loader and WSI. Native packet budgeting, scheduling
and completion belong to the backend. The user approved linking `vulkan-sgfx`,
SGFX core and the selected backend/codegen into one ICD/library, with no planned
independent SGFX Rust loading boundary. Internal Rust signatures, enum payloads,
trait requirements and dependency types can evolve with their consumers in the
same build. Direct Rust users must select compatible revisions and rebuild.
A blanket `#[non_exhaustive]` migration or all-exports 1.x freeze is not required
for RC1. Existing source interfaces and feature recipes are unchanged by this
policy update; the synchronous kernel ABI and SWS wire contracts remain separate.

VirGL scheduling and safe ScarletUI frame rejection, including prefix retirement
and application notification, are documented in the
[completion implementation boundary](../graphics/gpu-async-submission.md).
The user has also confirmed the Boxcraft
runtime repair. ScarletUI's Scene/Window, feature and extension rules and the
native libraries' ownership/error/mapping/GPU/SWS rules are recorded in the
contracts above.
A618 async work is deferred. Candidate dependency integration, remaining
conformance evidence, lint disposition and publication are still separate work.

The SWS exception concerns wire compatibility, not permission to break the
Rust source API of a released client crate. Update the server, low-level
client, direct protocol users, and UI platform adapter together when changing
the wire format. `GET_CAPABILITIES` reports a version and feature bits; it is
not a general old/new wire translation mechanism. The
[SWS protocol specification](../graphics/sws-ipc-protocol.md) remains canonical.

## Supported configurations to validate

| Configuration | Required evidence before declaring support |
| --- | --- |
| Host WGPU / ScarletUI | Host tests with Scarlet Rust, additional upstream portability tests, real adapter rendering/readback, and the recorded OS/adapter configuration. |
| RISC-V Scarlet | `riscv64gc-unknown-scarlet` with Rust `std`; locked userspace checks, kernel tests/build, and QEMU desktop exercise on the selected image. |
| AArch64 Scarlet | `aarch64-unknown-scarlet` with Rust `std`; the corresponding locked checks, kernel tests/build, and QEMU/VirGL desktop exercise. |
| Chromebook / Adreno A618 (deferred) | Work paused by the user on 2026-09-06. Support evidence would require the recorded Coachz/SC7180 board, firmware and driver configuration; hardware drawing, presentation, buffer lifetime, and submit validation. Cross-checks alone do not satisfy this row. |
| Legacy JSON userspace targets | Retain the existing two-architecture SGFX/UI build checks and compatibility features with the pinned compiler. These are legacy configurations, not the definition of a normal Scarlet target. |

The kernel remains `no_std`. Both normal Scarlet userspace targets support
Rust `std`. Record toolchain updates explicitly; a package version does not
promise compatibility with every nightly or freeze JSON target internals.
Support is limited to the configurations and operations actually verified in
the release evidence, not every host/board that compiles.

## Finite RC1 gates

1. **Contract review:** finish application-facing API review and the SGFX
   execution-semantics review, plus the separate `scarlet-sdk` tooling contract.
   Verify a consistent Rust integration set; do not require a blanket SGFX
   source API freeze.
   Add regression coverage for the supported boundaries; record
   explicitly named exceptions and unsupported operations. ABI layout and wire
   byte tests guard representations, not complete runtime semantics.
   The approved completion scope also requires actual asynchronous VirtIO/VirGL
   and A618 execution, native SGFX/facade receipts, and consumer resource
   retirement. A completed receipt wrapped around synchronous native submission
   does not pass this gate; neither does the additive kernel ABI by itself.
2. **Automated checks:** pass the existing locked dependency-identity, host,
   cross-target, kernel, and formatting checks. Disposition existing lint
   diagnostics and ignored/filtered tests individually or by a justified
   category, with a reproducer and follow-up. Do not call a disabled test a
   pass or add blanket lint allowances. Correctness failures remain blockers;
   an allocation optimization target need not become an unqualified API promise.
3. **Runtime and image checks:** complete input, resize, sustained frames, and
   repeated window close/reopen on the selected QEMU images, plus the A618
   hardware row. The user accepted comfortable operation of the current QEMU
   configuration on 2026-09-05; do not reopen its historical debug-only delay
   as a release blocker. Retain routine candidate regression checks. Build the
   selected full images from committed project locks. Retain coverage of the
   repaired `yt` cross-compiler selection and the external application graph.
   The SGFX diagnostic and dedicated image were removed at the user's request;
   do not recreate them as a release gate.
4. **Release rehearsal:** settle the shared Git-selector policy, rehearse the
   repository-level dependency cycles, and validate the exact candidate
   revision/lockfile set without unpublished sibling overrides. A matching
   version string does not prove that two `sgfx-core` sources are identical.
   Prepare lockfile-update PR automation without automatic merging.
5. **Publication review:** record support, limitations, check results, package
   inventory, and all source/toolchain/project locks in candidate notes. Only
   then bump versions and publish new immutable `v1.0.0-rc.1` tags. Validate
   published sources before announcing the candidate. Never move a tag to
   repair it; use the next RC. Final `v1.0.0` follows a successful RC review.

This policy neither waives the remaining runtime failures nor expands 1.0
into an obligation to finish every experimental subsystem.
