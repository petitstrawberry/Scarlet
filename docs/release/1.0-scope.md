# 1.0 release scope and compatibility policy

Status: target policy for the coordinated release, not a statement that the
current trees meet it. RC1 remains blocked on the gates below. Read this with
the [roadmap](1.0-roadmap.md) and [verification evidence](1.0-baseline.md).

## What is being released

The first coordinated release covers Scarlet, SGFX, ScarletUI, and the
Chromebook/Adreno integration. Align all **project-owned Cargo packages** in
the [inventory](1.0-packages.md), including applications, examples, fixtures,
tools, and BSPs, at `1.0.0-rc.1`, then `1.0.0`. Re-inventory at staging. Keep
vendored packages at their upstream versions and retain `publish = false`.
Version alignment is bookkeeping, not a claim that every example, device,
driver interface, or optional feature is a stable SDK.

Git distribution is sufficient. crates.io publication, a Vulkan frontend,
new backends, support for every Chromebook device, and completing all
experimental applications are not prerequisites. An experimental application
that is included in the chosen release image must still build: the label is
not permission to ship an unbuildable image. The existing full-image contents
are not reduced by this policy.

## Compatibility boundaries

| Boundary | 1.x target contract | Not implied |
| --- | --- | --- |
| Public Rust libraries | Preserve supported public types, functions, traits, feature names, and documented behavior within a major version. Additions must not break downstream code. | Stable Rust binary ABI, identical compiler internals, or compatibility between arbitrary Git snapshots. |
| Scarlet native userspace ABI | Preserve released syscall numbers, argument/result meanings, and the layouts of supported ABI records on each supported architecture. Introduce a new versioned record or operation for an incompatible extension. | A binary for one architecture running on another, or every syscall being implemented in every kernel configuration. |
| Generic GPU ABI | Preserve versioned request layouts, command/result values, capability checks, and the documented synchronous submit boundary. Keep ABI version fields independent of package versions. | Every execution dialect or GPU feature being supported, or submission implying display presentation. |
| SWS wire protocol | Ship and test a matched server/client/platform-adapter revision set. Keep optional operations capability-gated and preserve exact buffer generation/epoch/serial identity. | Compatibility with older independently installed clients. SWS remains an internal protocol under its existing policy; a package major number is not wire negotiation. |
| SGFX | Preserve the supported portable IR and public executor/facade contracts, including ordering, ownership, explicit unsupported-operation errors, and the existing acceptance boundary. | A portable GPU-completion token, cross-queue synchronization, transactional failure, or common device-loss recovery. These are not promised by 1.0 without an explicit API and tests. |
| ScarletUI | Preserve the supported application-facing view/state/layout/scene APIs, macros, and documented renderer/platform extension traits. | Pixel-identical rendering across hosts, a fixed frame rate, or an unconditional host-independent zero-allocation budget. |
| Kernel modules and board integration | Build and distribute external drivers/BSPs with the recorded kernel, toolchain, and project locks. Document the tested board and operations. | Stable Rust module ABI, arbitrary out-of-tree driver compatibility, or support for every device in the repository. |

The Rust compatibility rules follow the
[Cargo SemVer guidance](https://doc.rust-lang.org/cargo/reference/semver.html).
Treat externally reachable `pub` APIs as public by default. Do not silently
reclassify a difficult API as internal to make a release pass. Any experimental
exception must be named in the owning crate's documentation before RC1 and
reviewed with its users. Missing documentation does not make a public API
private. The export/feature review remains a gate, especially for SGFX's
backend boundary and ScarletUI's extension traits.

The SWS exception concerns wire compatibility, not permission to break the
Rust source API of a released client crate. Update the server, low-level
client, direct protocol users, and UI platform adapter together when changing
the wire format. `GET_CAPABILITIES` reports a version and feature bits; it is
not a general old/new wire translation mechanism. The
[SWS protocol specification](../graphics/sws-ipc-protocol.md) remains canonical.

## Supported configurations to validate

| Configuration | Required evidence before declaring support |
| --- | --- |
| Host WGPU / ScarletUI | Host tests with Scarlet Rust, additional upstream portability tests, real adapter rendering/readback, and the recorded OS/adapter configuration. |
| RISC-V Scarlet | `riscv64gc-unknown-scarlet` with Rust `std`; locked userspace checks, kernel tests/build, and QEMU desktop exercise on the selected image. |
| AArch64 Scarlet | `aarch64-unknown-scarlet` with Rust `std`; the corresponding locked checks, kernel tests/build, and QEMU/VirGL desktop exercise. |
| Chromebook / Adreno A618 | The recorded Coachz/SC7180 board, firmware and driver configuration; hardware drawing, presentation, buffer lifetime, and submit validation. Cross-checks alone do not satisfy this row. |
| Legacy JSON userspace targets | Retain the existing two-architecture SGFX/UI build checks and compatibility features with the pinned compiler. These are legacy configurations, not the definition of a normal Scarlet target. |

The kernel remains `no_std`. Both normal Scarlet userspace targets support
Rust `std`. Record toolchain updates explicitly; a package version does not
promise compatibility with every nightly or freeze JSON target internals.
Support is limited to the configurations and operations actually verified in
the release evidence, not every host/board that compiles.

## Finite RC1 gates

1. **Contract review:** finish the public export/feature review in the four
   repositories. Add regression coverage for the supported boundaries; record
   explicitly named exceptions and unsupported operations. ABI layout and wire
   byte tests guard representations, not complete runtime semantics.
2. **Automated checks:** pass the existing locked dependency-identity, host,
   cross-target, kernel, and formatting checks. Disposition existing lint
   diagnostics and ignored/filtered tests individually or by a justified
   category, with a reproducer and follow-up. Do not call a disabled test a
   pass or add blanket lint allowances. Correctness failures remain blockers;
   an allocation optimization target need not become an unqualified API promise.
3. **Runtime and image checks:** complete input, resize, sustained frames, and
   repeated window close/reopen on the selected QEMU images, plus the A618
   hardware row. Record time to first frame and investigate stalls. Build the
   selected full images from committed project locks. Retain coverage of the
   repaired `yt` cross-compiler selection and the external application graph;
   the focused SGFX smoke image does not replace this gate.
4. **Release rehearsal:** settle the shared Git-selector policy, rehearse the
   repository-level dependency cycles, and validate the exact candidate
   revision/lockfile set without unpublished sibling overrides. A matching
   version string does not prove that two `sgfx-core` sources are identical.
   Prepare lockfile-update PR automation without automatic merging.
5. **Publication review:** record support, limitations, check results, package
   inventory, and all source/toolchain/project locks in candidate notes. Only
   then bump versions and publish new immutable `v1.0.0-rc.1` tags. Validate
   published sources before announcing the candidate. Never move a tag to
   repair it; use the next RC. Final `v1.0.0` follows a successful RC review.

This policy neither waives the remaining runtime failures nor expands 1.0
into an obligation to finish every experimental subsystem.
