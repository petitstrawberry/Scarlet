# Coordinated 1.0 release

Status: preparation in progress; the next milestone is `1.0.0-rc.1` for
Scarlet, SGFX, ScarletUI, and the Chromebook/Adreno integration. This document
is a release checklist, not a declaration that today's APIs are stable.

The first release aligns these projects at 1.0. Subsequent versions should
follow each project's own compatibility changes. Git distribution remains
supported; publishing on crates.io is not a prerequisite.

See the [2026-09-05 migration baseline](1.0-baseline.md) for the published
revision set, CI runs, local verification, and known failures.

The [release scope and compatibility policy](1.0-scope.md) defines the target
support boundaries, package membership, and finite RC1 gates. It is not a
claim that the current APIs or runtime checks have passed release review.

## Compatibility decisions before RC1

Under [SemVer](https://semver.org/spec/v2.0.0.html), 1.0 defines the public API.
The following boundaries need explicit, reviewed contracts before the release:

| Project | Boundary to review | Decision needed |
| --- | --- | --- |
| Scarlet | Native userspace ABI, runtime/SDK APIs, GPU ABI, SWS protocol | Which interfaces preserve source or binary compatibility, which are private, and how clients negotiate supported versions |
| SGFX | Portable IR and the complete backend execution contract | Validation, resource lifetimes, submission/completion, synchronization, capabilities, and unsupported-operation errors |
| ScarletUI | App-facing widgets/state/layout and renderer/platform integration | Supported public APIs and features, extension points, and the boundary between public contracts and implementation details |
| Chromebook / Adreno | SGFX backend, code generation, and userspace/kernel submit format | Supported A618 operations, resource authority, wire compatibility, and the hardware support baseline |

In particular, the current [SWS protocol policy](../graphics/sws-ipc-protocol.md)
allows incompatible internal wire changes. A 1.0 package number must not
silently turn that into a promise of old-client compatibility. Decide and
document the policy, then test it.

SGFX's direction is tracked in
[SGFX #1](https://github.com/petitstrawberry/sgfx/issues/1). Resolve changes that
affect the public IR/backend boundary before stabilizing that boundary.
Completing a Vulkan frontend or every future backend is not a release gate.

Package versions, Rust source compatibility, and wire/ABI version fields are
different things. Do not reset `GPU_ABI_VERSION`, `SWS_PROTOCOL_VERSION`, or
Adreno's submit-wire versions to match the package version. Keep vendored
third-party package versions unchanged, and inventory the first-party release
packages before editing their manifests.

local integration tests. Such results are provisional: do not commit those
alternate lockfiles or report them as a successful published-source build.

## B. Establish the verification baseline

The primary compiler is `scarlet-rust-toolchain`, including for host tests.
CI uses the same pinned `scarlet-rust-nix` revision as Scarlet's `flake.lock`:
`2b4ddd555389a8c53806bbc2586440b2662c38dd`. Upstream
`nightly-2025-12-31` is an additional portability check, not a substitute for
testing Scarlet's compiler.

| Check | Compiler | Required coverage |
| --- | --- | --- |
| Host | Scarlet Rust | SGFX portable crates, ScarletUI including its SGFX renderer, Adreno codegen and the real kernel submit validator |
| Host portability | Upstream Rust | The same host suites, without requiring Scarlet-specific compiler support |
| RISC-V userspace | Scarlet Rust | `riscv64gc-unknown-scarlet`, std-enabled SGFX, UI/SWS, Adreno backend, and Scarlet applications |
| AArch64 userspace | Scarlet Rust | `aarch64-unknown-scarlet`, the same std-enabled integration |
| Kernel | Scarlet Rust / Scarlet build environment | Existing `cargo make` build, test, formatting, and lint tasks for both architectures |

Both normal Scarlet userspace targets support Rust `std`. The kernel is
`no_std`; the legacy JSON userspace targets and `legacy-scarlet-std` feature
are a separate compatibility configuration. Keep their checks while they are
supported and decide their release support policy explicitly.

- [x] Run SGFX, ScarletUI, and Adreno workflows on the published dependency graph
  using `--locked`; do not let CI silently repair an outdated lockfile.
- [x] Keep Scarlet and upstream build artifacts in separate target directories.
  Any future CI cache key must distinguish compiler revision and target.
- [x] Require the SGFX source-identity checks in SGFX, ScarletUI, and Adreno CI
  on host and both Scarlet targets.
  `cargo tree --locked --invert sgfx-core` fails on an ambiguous package name,

- [x] Verify Scarlet's own std and legacy SGFX integration checks in CI.
- [x] Establish a clean-source, all-binaries std userspace baseline, including
  SWS, on both Scarlet targets. The SWS direct `gpu-raw` dependency is declared
  separately from the SGFX migration, and CI now checks `--bins` rather than
  only the SGFX demos.
- [x] Restore ScarletUI's filtered allocation-budget regression to both host
  CI compiler suites; the unfiltered Linux runs passed.
- [x] Make the 19 core and four proc-macro documentation examples testable.
  Both host compilers run the unfiltered workspace and preview-enabled macro
  examples. The sole remaining ignored test is the explicitly manual PPM
  visual-dump helper, not an automated correctness or runtime gate.
- [ ] Resolve or explicitly disposition existing compiler and Clippy warnings
  before final 1.0. The macro library passes strict Clippy; other UI and kernel
  diagnostics remain a separate release gate.
- [ ] Add contract tests for the public boundaries identified above; compile
  checks alone do not establish runtime or binary compatibility.

`cargo make test-release-contracts` now runs host-native ABI representation
tests and the SWS protocol suite, including literal wire fixtures and malformed
shared-frame rejection cases. CI runs it with Scarlet Rust. This is initial
boundary coverage, not completion of the export/feature or runtime review.

SGFX's current
[execution contract](https://github.com/petitstrawberry/sgfx/blob/b6e4b5ecf3dd90ec0700173debf977c10cf5920d/docs/execution-contract.md)
now distinguishes queue acceptance, GPU completion, upload ownership,
imported-image release, and non-transactional errors. Real WGPU tests cover
same-queue ordering, upload-storage reuse, dropping backend owners before
waiting, resource-table identity, and late-upload rejection. Portable
completion/capability APIs and fault recovery remain decisions, not promises
established by these success-path tests.

## C. Prepare immutable Git releases and updates

- [x] Record the [post-migration Cargo package inventory](1.0-packages.md),
  distinguishing first-party packages, development fixtures, and vendored code.

- [x] Define release package membership: align all project-owned packages in
  the inventory, including fixtures, without changing vendored versions or
  treating every package as a supported SDK.
- [ ] Re-inventory at staging and set the selected Cargo versions to
  `1.0.0-rc.1` only after the RC gates are satisfied;
  use `v1.0.0-rc.1` for the new Git tags. Preserve historical tags.
- [ ] Decide and test one consistent Git-reference policy for every shared
  SGFX type. Git tags are exact sources, not Cargo SemVer ranges: independently
  upgrading a tag can duplicate `sgfx-core` even within the same major version.
- [ ] Rehearse release staging before tagging. SGFX's facade depends on
  external Adreno, which imports SGFX core; SGFX also imports Scarlet runtime
  crates. The Rust crate graph is acyclic, but repository-level references are
  not a simple one-way release chain. Dependency tags must resolve before a
  candidate is announced; do not move an already published tag to fix it.
- [ ] Record the exact four-repository revision set and relevant toolchain,
  project, and Cargo lockfiles in the release evidence.
- [ ] Add dependency-update PR automation, with all integration gates required.
  Bare Git dependencies currently need an explicit lockfile-update workflow;
  do not assume Renovate's Git-tag or revision tracking covers them.
- [ ] Publish RC1 only after reviewing the compatibility policy, check results,
  remaining limitations, and release notes.
- [ ] Iterate with new RC versions as needed, then publish `v1.0.0` after the
  final compatibility and runtime gates pass. Never overwrite release tags.

Creating a candidate or a stable release is a separate publication step; this
checklist and the CI preparation do not create tags or GitHub releases.
