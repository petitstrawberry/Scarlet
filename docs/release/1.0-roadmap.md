# Coordinated 1.0 release

Status: preparation in progress; the next milestone is `1.0.0-rc.1` for
Scarlet, SGFX, ScarletUI, and the Chromebook/Adreno integration. This document
is a release checklist, not a declaration that today's APIs are stable.

The first release aligns these projects at 1.0. Subsequent versions should
follow each project's own compatibility changes. Git distribution remains
supported; publishing on crates.io is not a prerequisite.

See the [2026-09-05 migration baseline](1.0-baseline.md) for the published
revision set, CI runs, local verification, and known failures.

The [release scope and compatibility policy](1.0-scope.md) defines the target
support boundaries, package membership, and finite RC1 gates. It is not a
claim that the current APIs or runtime checks have passed release review.

## Compatibility decisions before RC1

Under [SemVer](https://semver.org/spec/v2.0.0.html), 1.0 defines the public API.
The [release scope](1.0-scope.md) selects the compatibility boundaries below.
Detailed contract decisions and implementation conformance are separate gates:

| Project | Selected boundary | Remaining contract work |
| --- | --- | --- |
| Scarlet | Stable released native/GPU ABI records and operations; source-compatible public SDK; matched-set internal SWS wire | Specify extension/error rules and ownership for the concrete SDK/GPU/SWS operations; preserve independent ABI/wire version fields |
| SGFX | Portable drawing/transfer IR and public backends; owned completion tracking and actual asynchronous Scarlet submission | The user approved the [completion direction](https://github.com/petitstrawberry/sgfx/blob/90eb0641cf3dbdb415db6c48d81f7bf224d99984/docs/completion-contract.md). Core/WGPU are implemented; native driver/consumer integration remains. Other [1.0 policies](https://github.com/petitstrawberry/sgfx/blob/90eb0641cf3dbdb415db6c48d81f7bf224d99984/docs/1.0-contract.md) are a draft, not blanket user approval |
| ScarletUI | Source-compatible app-facing view/state/layout/scene APIs, macros, and renderer/platform extension traits | Specify identity, cloning/state sharing, scene/window lifecycle, and extension rules; retain the agreed `View`/`ViewClone` architecture |
| Chromebook / Adreno | Public backend obeys the SGFX contract; kernel/BSP integration is a recorded matched set | Specify supported A618 operations, resource authority and submit-wire extension/error rules against the SGFX decisions |

In particular, the current [SWS protocol policy](../graphics/sws-ipc-protocol.md)
allows incompatible internal wire changes. Keep that matched-set policy: a
1.0 package number does not promise old-client compatibility. Specify and
test capability-gated operations and exact frame identities under that policy.

SGFX's direction is tracked in
[SGFX #1](https://github.com/petitstrawberry/sgfx/issues/1). Resolve changes that
affect the public IR/backend boundary before stabilizing that boundary.
Completing a Vulkan frontend or every future backend is not a release gate.

Package versions, Rust source compatibility, and wire/ABI version fields are
different things. Do not reset `GPU_ABI_VERSION`, `SWS_PROTOCOL_VERSION`, or
Adreno's submit-wire versions to match the package version. Keep vendored
third-party package versions unchanged, and inventory the first-party release
packages before editing their manifests.

### Contract-first work order

1. Record concrete guarantees and non-guarantees for each public boundary.
   Portable completion tracking and actual asynchronous Scarlet GPU submission
   are approved for SGFX 1.0. Implement that direction while preserving existing
   synchronous operations. Other SGFX extension/rendering/lifecycle policies
   remain draft proposals to review, not previously approved decisions.
2. Specify ScarletUI's view/state/scene and extension contracts, then the
   concrete Scarlet SDK/GPU/SWS and Adreno boundary rules above. Classify each
   incompatibility as a deliberate pre-1.0 change or an implementation defect.
3. Implement and test those named differences. Additional validation/CI
   coverage does not substitute for deciding the behavior being tested.
   Resume full release verification and staging after the contract work.

The SGFX design reference and new core/WGPU implementation are newer than the
consumer dependency revision below. They do not update application lockfiles,
approve every draft policy, or certify native failure/teardown safety. See the
[completion implementation boundary](../graphics/gpu-async-submission.md) for
what the Scarlet kernel currently implements and what its drivers still lack.
VirtIO/VirGL now implements real async enqueue and independently driven
retirement, verified on AArch64 QEMU with PCI/two CPUs and MMIO/one CPU. A618
and the native SGFX/SWS/UI consumers are not yet on that path.

## B. Establish the verification baseline

The primary compiler is `scarlet-rust-toolchain`, including for host tests.
CI uses the same pinned `scarlet-rust-nix` revision as Scarlet's `flake.lock`:
`2b4ddd555389a8c53806bbc2586440b2662c38dd`. Upstream
`nightly-2025-12-31` is an additional portability check, not a substitute for
testing Scarlet's compiler.

| Check | Compiler | Required coverage |
| --- | --- | --- |
| Host | Scarlet Rust | SGFX portable crates, ScarletUI including its SGFX renderer, Adreno codegen and the real kernel submit validator |
| Host portability | Upstream Rust | The same host suites, without requiring Scarlet-specific compiler support |
| RISC-V userspace | Scarlet Rust | `riscv64gc-unknown-scarlet`, std-enabled SGFX, UI/SWS, Adreno backend, and Scarlet applications |
| AArch64 userspace | Scarlet Rust | `aarch64-unknown-scarlet`, the same std-enabled integration |
| Kernel | Scarlet Rust / Scarlet build environment | Existing `cargo make` build, test, formatting, and lint tasks for both architectures |

Both normal Scarlet userspace targets support Rust `std`. The kernel is
`no_std`; the legacy JSON userspace targets and `legacy-scarlet-std` feature
are a separate compatibility configuration. Keep their checks while they are
supported and decide their release support policy explicitly.

  `cargo tree --locked --invert sgfx-core` fails on an ambiguous package name,

- [x] Restore ScarletUI's filtered allocation-budget regression to both host
  CI compiler suites; the unfiltered Linux runs passed.
- [x] Make the 19 core and four proc-macro documentation examples testable.
  Both host compilers run the unfiltered workspace and preview-enabled macro
  examples. The sole remaining ignored test is the explicitly manual PPM
  visual-dump helper, not an automated correctness or runtime gate.
- [ ] Resolve or explicitly disposition existing compiler and Clippy warnings
  before final 1.0. The macro library passes strict Clippy; other UI and kernel
  diagnostics remain a separate release gate.
- [ ] Add contract tests for the public boundaries identified above; compile
  checks alone do not establish runtime or binary compatibility.

`cargo make test-release-contracts` now runs host-native ABI representation
tests and the SWS protocol suite, including literal wire fixtures and malformed
shared-frame rejection cases. CI runs it with Scarlet Rust. This is initial
boundary coverage, not completion of the export/feature or runtime review.

SGFX's current
[execution contract](https://github.com/petitstrawberry/sgfx/blob/0e9102358ed302d6703a22b892a00be38abba8cb/docs/execution-contract.md)
now distinguishes queue acceptance, GPU completion, upload ownership,
imported-image lifetimes, and non-transactional errors. Real WGPU tests cover
same-queue ordering, upload-storage reuse, dropping backend owners before
waiting, resource-table identity, and late-upload rejection. Since that consumer
baseline, SGFX `90eb0641` adds `CommandSubmitter`, owned `Completion` receipts,
bounded WGPU tracking, and partial-acceptance error receipts. Its 45 portable
tests pass with Scarlet Rust and upstream Rust, including real Metal execution.
The native backend/facade is not yet on that path. These host results do not
establish native async submission, imported-image retirement, or fault safety.

The [SGFX public API inventory](https://github.com/petitstrawberry/sgfx/blob/0e9102358ed302d6703a22b892a00be38abba8cb/docs/1.0-api-scope.md)
now records the implemented drawing/transfer subset, target-dependent exports,
runtime/backend feature composition, and native/direct APIs that remain
public. Core depth-attachment validation and WGPU upload/size rejection have
regression coverage; the portable suite has 35 default-configuration tests.
Both host compilers additionally test the backend-free and WGPU-only facade
configurations, and CI checks public Rustdoc with warnings denied on host and
both Scarlet targets. The newer contract draft proposes open/closed enum rules,
rendering conventions, trait/struct/feature boundaries and imported-image
retirement. Those proposals still require review. The approved completion work
does not implicitly approve them; test counts are not an API-freeze claim.

### Runtime release evidence

- [x] VirtIO async driver checkpoint: bounded multiple submissions, independent
  completion, exact clear/readback, detach ordering and closed observer/owner
  lifetimes in real QEMU runs. The focused image includes the opt-in
  `gpu-async-smoke` diagnostic. This does not complete native SGFX consumer

  A headless CI run that skips rendering is not sufficient evidence.

  operation without delay on 2026-09-05 and approved proceeding on that basis.
  The old debug-build timing is not an open release blocker. Preserve the
  [focused AArch64 fixture](../../projects/aarch64-sgfx-smoke/README.md) for
  regression checks and record final candidate pins at release staging.
- [ ] A618 hardware: run a representative UI workload and record drawing,
  presentation, resource lifetime, and submit-validation results on the
  supported Chromebook configuration.
- [ ] Record unsupported features and the exact tested configuration in the
  release notes. Do not infer hardware support from a successful cross-check.

- [x] Define release package membership: align all project-owned packages in

- [ ] Re-inventory at staging and set the selected Cargo versions to
  `1.0.0-rc.1` only after the RC gates are satisfied;
  use `v1.0.0-rc.1` for the new Git tags. Preserve historical tags.
- [ ] Decide and test one consistent Git-reference policy for every shared
  SGFX type. Git tags are exact sources, not Cargo SemVer ranges: independently
  upgrading a tag can duplicate `sgfx-core` even within the same major version.
- [ ] Rehearse release staging before tagging. SGFX's facade depends on
  external Adreno, which imports SGFX core; SGFX also imports Scarlet runtime
  crates. The Rust crate graph is acyclic, but repository-level references are
  not a simple one-way release chain. Dependency tags must resolve before a
  candidate is announced; do not move an already published tag to fix it.
- [ ] Record the exact four-repository revision set and relevant toolchain,
  project, and Cargo lockfiles in the release evidence.
- [ ] Add dependency-update PR automation, with all integration gates required.
  Bare Git dependencies currently need an explicit lockfile-update workflow;
  do not assume Renovate's Git-tag or revision tracking covers them.
- [ ] Publish RC1 only after reviewing the compatibility policy, check results,
  remaining limitations, and release notes.
- [ ] Iterate with new RC versions as needed, then publish `v1.0.0` after the
  final compatibility and runtime gates pass. Never overwrite release tags.

Creating a candidate or a stable release is a separate publication step; this
checklist and the CI preparation do not create tags or GitHub releases.
