# Scarlet Native SDK contract

Status: current-behavior baseline for the coordinated 1.0 release, adopted on
2026-09-06 with the approved pre-1.0 unsafe-boundary correction. This specifies
the SDK boundary; it does not publish 1.0 or certify untested hardware. Read it
with the [release scope](1.0-scope.md),
[GPU completion contract](../graphics/gpu-async-submission.md),
[SWS client contract](../graphics/sws-client.md) and
[wire specification](../graphics/sws-ipc-protocol.md).

## Layers and public surface

| Layer | Contract |
| --- | --- |
| `scarlet-abi` | Dependency-free `no_std` syscall identifiers, constants and ABI records; released numbers, layouts and operation meanings are versioned independently of Cargo package versions |
| `scarlet-sys` | Raw `unsafe` syscall entry points and ABI reexports; returns the unmodified kernel result, without imposing one universal errno encoding |
| `scarlet-os` | Typed Handle/capability, input, IPC, network, poll, process, scheduler, sensor, socket, time and hypervisor APIs; raw address/control/callback operations retain explicit unsafe obligations |
| `scarlet-rt` | Process entry, environment, termination and optional allocator/panic glue; default features do not install an allocator, entry symbol or panic handler |
| `scarlet_std` | Legacy `scarlet-std` package API and reexports, including the same unsafe raw entry points; not the normal Rust `std` port |
| Native clients | `gpu-raw`, `sws-client`, framebuffer/audio/video and service clients layer their documented protocols and lifetimes over those primitives |

Externally reachable public Rust APIs are public by default. Preserve supported
functions, types, fields, variants, traits, feature names and documented behavior
within a released major version. Adding a variant to an exhaustive enum or a
required trait method is not automatically compatible. An incompatible extension
needs an explicit migration/version decision; do not reinterpret an old ABI
record, syscall number or control command in place.

This is a source and native-ABI contract, not a stable Rust binary ABI or a
promise of compatibility between arbitrary Git snapshots. Select a matched
source/lock/toolchain set. SGFX's separately approved coordinated Rust-internals
policy does not waive these application-facing SDK guarantees.

## Features and targets

Normal userspace uses Rust `std` on `aarch64-unknown-scarlet` or
`riscv64gc-unknown-scarlet` and explicit Scarlet crates for native operations.
The kernel remains `no_std`. Legacy runtime applications opt into the legacy
crate/feature recipes; do not combine their allocator/entry/panic ownership with
normal Rust `std` in one executable.

`scarlet-os` itself is `no_std`; `std` selects standard environment/file access
where needed. Its default `rt-env` feature uses `scarlet-rt` environment support
for legacy callers. `scarlet-rt`'s `allocator`, `entry` and `panic` features are
opt-in runtime components, not defaults to enable in every application. Client
crates with std/legacy modes must use the same runtime choice as their consumer.
An all-features or mixed std/legacy workspace build is not a supported recipe.

A type or syscall being available at compile time does not promise that a
kernel configuration, device or platform implements it. Report its existing
unsupported/capability error; do not silently emulate stronger guarantees.
Package version alignment does not change GPU ABI or SWS wire version fields.

## Unsafe boundary

Kernel pointer/range checks do not prove Rust validity, aliasing or ownership.
For example, unmapping an otherwise valid address can invalidate a live Rust
reference. The following low-level entries therefore require `unsafe`:

- `scarlet_sys::syscall0` through `syscall6`: correct operation/argument ABI,
  pointer layout, alignment, access permissions, lifetime, ownership transfer
  and any effects on mappings, stacks or TLS. The requirement also applies to
  zero-argument entry points because the operation is selected dynamically.
- `Handle::control`, raw VM/vCPU control: exact command-specific scalar/record
  ABI and nested-pointer lifetimes; output storage must be exclusively writable.
- Handle-backed/anonymous `mmap` and both `munmap` forms: authority over the
  affected virtual range, no invalidation of live references/allocations/code/
  stacks, and coordinated shared/device backing access.
- Runtime `brk`/`sbrk`, TLS setters and legacy raw `clone`: preserve allocator,
  thread, stack, TLS and Rust ownership invariants across all affected contexts.
- Guest-memory registration: host backing remains valid for all guest accesses,
  including through other VM/vCPU handles; guest writes must not race or alias
  unsynchronized Rust accesses.
- Event-handler registration and raw event return: executable non-unwinding
  handlers with the native ABI, safe asynchronous reentrancy, no retained
  `EventInfo` borrow, and return only from a live kernel event frame.

These are deliberate pre-1.0 Rust source changes. Syscall/control numbers,
records, calling convention and kernel execution behavior are unchanged. Safe
typed operations remain safe by supplying the fixed ABI, borrowed buffers and
ownership internally. Private scalar-only control helpers do not expose an
arbitrary public forwarding API. Ordinary file/socket operations, `fork` and
the `Send + 'static` thread-spawn wrapper do not require callers to invoke raw
syscalls themselves.

Callers of raw mapping APIs receive addresses, not RAII guards or Rust borrows
of the Handle. A mapping is not automatically unmapped when a capability view
is dropped. Creating a raw pointer does not authorize dereferencing it: ensure
backing lifetime, protection, bounds, aliasing and synchronization at each access.
Shared-memory access needs coordination with other mappings/processes/devices.
Releasing a CPU virtual mapping and retiring independently pinned kernel/device
backing are distinct operations.

## Handles and ownership transfer

`Handle` is an owning, non-Copy wrapper. `as_raw` and capability views borrow it;
they do not transfer ownership. `duplicate` returns a new independently owned
handle referring to the same kernel object. `from_raw` is unsafe and consumes
exclusive ownership even if its validation fails: failure closes the raw handle.
Do not create two owners for one numeric handle or close it behind a live owner.

Drop closes an armed Handle once. Explicit consuming `close` disarms Drop before
the kernel request, including on error; it does not retry a failed close during
Drop. This rule applies to Handle owners, not every API returning a raw integer.
In particular, raw hypervisor handles and guest addresses do not acquire Handle
RAII semantics merely because they are wrapped in a VM convenience type.

`SharedMemory::from_handle` and `Socket::from_handle` take ownership by value:
success retains the Handle, failure drops/closes it. Their previous claim that
failure did not consume the handle was incorrect and is corrected in Rustdoc.
`Socket::from_raw` also consumes its input, including validation/panic paths.

Capability-view construction checks the cached object kind/capability metadata;
its constructor is private. Obtaining a view does not mean every command, mapping
mode or backend operation is supported. The kernel still validates the operation.
Sending a borrowed Handle through the socket capability API duplicates it for
the receiver, leaving the sender's owner intact. Receiving a Handle transfers
new ownership and the receiving wrapper validates/adopts it.

## Results, partial work and observations

Use the result/error type of the specific API. Raw syscalls return raw values;
many typed wrappers use `HandleError`, some mapping/hypervisor operations retain
`Result<_, ()>`, and service clients have protocol-specific errors. There is no
new universal error conversion in this baseline.

Stream reads/writes may return short counts. `read_exact` and `write_all` may
make progress before an error and do not roll it back. End-of-stream, interrupted
and would-block results remain distinct under the stream wrapper's current
encoding. An error does not generally promise that no work was accepted or no
observable effect occurred; only rely on such a guarantee where the API states it.

`poll` borrows its handle array for the call and reports readiness. Readiness is
not successful completion, ownership transfer, GPU retirement or presentation.
A ready descriptor can still produce an operation-specific error.

## GPU and SWS integration

Keep the existing synchronous GPU operation meanings. Tracked GPU submission
copies the caller's commands before returning, owns accepted in-flight kernel
work independently of the submission/queue/context owner's later Drop, and
returns an observation receipt. Async capacity zero means unsupported, not Busy;
do not disguise synchronous execution as tracked asynchronous support.

`GpuSubmitError` distinguishes Busy, definite rejection and a failure that may
carry a receipt for accepted work. Absence of a receipt is not evidence of no
acceptance. A successful completion query only returns an observation: inspect
Pending/Complete/Failed. Failure or poll readiness alone does not prove quiescence.
Completion does not promise cross-queue ordering, CPU cache visibility, display
presentation, or release of an imported/SWS image lease. Formats, import paths
and optional operations remain bounded by the actual device capabilities.

SWS client connections own transport/request routing. Dispatch drains available
traffic and queues asynchronous events; synchronous responses are correlated by
request identity. Dropping a request token abandons local response tracking, not
server-side work or an externally retained buffer use.

Shared-frame registration transfers a duplicate Handle and receives the matching
registration identity. `commit_sgfx_frame` is one-way serialization, not a GPU or
compositor acknowledgment. Retain the exact
`(window_id, buffer_id, generation, compositor_epoch, commit_serial)` until its
release/rejection event. Destruction follows release and waits for its matching
response. Do not release an image merely because another generation or commit
was released, or because its render completed.

CPU `Surface` mappings and borrowed buffer access remain scoped to the owning
surface/remap lifecycle. They are not a substitute for the external SGFX-frame
lease protocol. SWS wire remains an internal matched-set protocol: update server,
client, direct protocol users and UI adapter together. Rust client compatibility
and wire compatibility are separate promises.

## Evidence and remaining release work

Compile-fail Rustdoc tests enforce the unsafe raw syscall/control/mapping entry
points, without executing native syscalls. Consumer cross-checks establish that
the selected normal/legacy source sets follow the corrected signatures. ABI
representation and literal SWS wire fixtures remain in the existing
`cargo make test-release-contracts` gate; no ABI/wire layout changed here.

The [handoff](2026-09-06-sgfx-scarletui-handoff.md) records exact checks, local
dependency overrides and their limits. Published-source locks, candidate image
checks, fault/reset conformance and release notes remain separate. Boxcraft is
user-confirmed complete. A618 implementation/hardware work remains deferred;
signature-only consumer adaptations do not claim new A618 functionality.
