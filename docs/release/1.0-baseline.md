## Diagnosed CI failures

The [AArch64 failure at Scarlet `1991dd16`](https://github.com/petitstrawberry/Scarlet/actions/runs/33891757736)
was in `test_deferred_release_migrates_ready_task`. Its fixture marked a
synthetic CPU 1 online without booting its interrupt controller. Enqueuing a
task on that CPU attempted a real reschedule IPI and panicked with
`online CPU must accept reschedule IPI: source_cpu=0 target_cpu=1`.
Commit `4f209dc3` corrects the four affected queue-policy fixtures by modeling
an already in-flight IPI. It does not change production IPI delivery or remove
the queue/migration assertions. The dedicated IPI coalescing test remains.

The later [failure at `a194f4b5`](https://github.com/petitstrawberry/Scarlet/actions/runs/33944938089)
occurred in both userspace integration steps, before the kernel tests ran.
Nix's host Clang wrapper injected Linux glibc headers into the Scarlet-target
`ring` C build, causing `_FORTIFY_SOURCE` and missing `gnu/stubs-32.h` errors.
Commit `c99a35bb` supplied target-specific unwrapped Clang. Follow-up `6d511446`
changes this to the lower-priority `TARGET_CC` fallback so external application
settings are respected. This is a C cross-compilation environment correction,
not a change from Rust std to no_std.

The [subsequent CI run](https://github.com/petitstrawberry/Scarlet/actions/runs/33945632075)
passed both kernel suites (RISC-V 1157 and AArch64 1128 tests) and all other
jobs. The suites also passed again locally while verifying the SWS manifest
follow-up. Existing Clippy diagnostics are a separate unresolved baseline,
not the cause of either failed CI run.

## Native ABI and SWS contract-test follow-up

The [1.0 scope policy](1.0-scope.md) separates public Rust API compatibility,
native and GPU ABI versions, SWS matched-set wire compatibility, and tested
hardware support. Package membership is now all project-owned crates, with
vendored versions and test-harness publication restrictions preserved.

`cargo make test-release-contracts` passed under Scarlet Rust on
macOS/AArch64: 6 native ABI tests, 6 SWS golden-wire/negative tests, and all
29 existing SWS unit tests. No tests were skipped or filtered in this task.
The native tests pin syscall numbers, record sizes/alignment/field offsets,
versioned headers, reserved-field defaults, and unknown scheduler result/status
handling. SWS tests use literal bytes independently of the encoders, covering
routing, capabilities, the full shared-buffer identity, and malformed or
oversized frame damage. The task runs from the repository root with an explicit
host target, without selecting crate-local legacy target configurations. CI
now invokes it with the primary compiler.

These are representation/parser contracts, not evidence that the kernel and
userspace copies of every ABI match, that every syscall is stable, or that a
compositor releases resources at the correct time. GPU ABI parity, the public
export review, and runtime gates remain separate work.

Staged-source precommit verification passed formatting, these 41 contract
and protocol tests, 7 QMP tests, both locked std/legacy integration checks,
1157 RISC-V and 1128 AArch64 kernel tests, both full build tasks, and workflow
validation. The userspace Cargo lockfile stayed unchanged. Strict kernel
Clippy still reports the existing 1110-diagnostic baseline. The user's local
full-project lockfile changes were excluded and preserved.

## ScarletUI macro-contract follow-up

ScarletUI `73d17c3a` makes all four proc-macro documentation examples executable
and repairs a recursive element-creation path in `#[derive(View)]`. The old
derive wrapped itself in `ComponentElement::new`, whose default child builder
cloned that same View and called `create_element()` again. A bounded-clone
fixture reproduced that recursion before the fix.

Reusable components now opt in to an explicit child method with
`#[view(body = method_name)]`. The component retains the state-owning View and
uses the method for creation and rebuild. Scene-only application types keep
their existing body-less derive: the runner collects their listenables and
builds windows from `Application::scenes()`. Neither the Application/Scene
implementation nor the `View`/`ViewClone` trait design changed. Directly
mounting a body-less derive reports a configuration panic instead of recursing.

Seven new tests cover body selector parsing, shared State/default IDs, retained
children across rebuilds, scene-only applications, and the configuration
diagnostic. The staged host workspace passed **457 tests with 0 filtered**
under both Scarlet Rust and upstream `nightly-2025-12-31` on macOS/AArch64.
The only remaining ignored test is the explicitly manual visual-dump helper.
Four macro doctests also passed separately with `preview` enabled, exercising
three real registrations and the factory-created session's title and size.
The ordinary workspace run checks the preview-disabled path. Commit
`8c9a8138` adds the enabled configuration to both host CI compiler jobs.
All four jobs in its
[published Linux CI](https://github.com/petitstrawberry/scarlet-ui/actions/runs/33958583897)
passed, including both host compilers and both Scarlet targets.
Formatting, workflow validation, strict macro-library Clippy, and std-enabled
UI/SWS checks on both Scarlet targets passed. Existing warnings elsewhere in
ScarletUI are not waived by the macro-library Clippy result.

Unrelated widget-factory edits were excluded and preserved. A scratch sibling
override first checked Scarlet's existing std applications and legacy
`settings`/`ui-demo` on both architectures without changing their source.
The subsequent Git-only integration in Scarlet `4704a0f3` selects published ScarletUI `8c9a8138`
and SGFX `b6e4b5ec` in `.cargo/Cargo.lock`; the SGFX delta from the runtime
baseline is documentation and tests only. No package version, manifest Git
selector, project lockfile, or release tag is changed by this follow-up.
After removing the sibling override, the Git-only staged tree passed both
locked std/legacy integration tasks, formatting, the 41 ABI/SWS tests, five
cross-compiler fixture cases, seven QMP tests, 1157 RISC-V and 1128 AArch64
kernel tests, and both full build tasks. These checks used Scarlet Rust and

the existing 1110-diagnostic baseline; it is still not a passing lint gate.

## QEMU desktop follow-up

The [focused AArch64 project](../../projects/aarch64-sgfx-smoke/README.md)
builds successfully from the source tree published as Scarlet `beefb800`,
including the SWS bulk-initialization fix `28fdfc2d`. The tested host is
macOS/AArch64, using the same
pinned Scarlet Rust dev shell as above, QEMU `11.0.91-scarlet`, TCG,
`virtio-gpu-gl-pci`, `cocoa,gl=on`, 2 GiB RAM, a 1280x800 output at scale 2,
and both 1- and 4-vCPU configurations. Disk writes used snapshots; networking
was disabled with `-nic none`.

These measurements used the debug smoke image, without `--release`. The build
logs identify SWS and `ui-sgfx-showcase` as `dev` profile
`[unoptimized + debuginfo]`. They are not release-performance measurements.
On 2026-09-05 the user confirmed comfortable operation without visible delay
in the current QEMU configuration and explicitly accepted that runtime
baseline for continued release work. Treat this as completed user acceptance,
not as a request for another timing reproduction. The earlier debug-only
observation is not an outstanding release-performance defect. This acceptance
is for the current QEMU configuration, not a claim about every hardware backend.

The QEMU source pin in `flake.lock` is
`13299d8d5462278f6f03d744ff2d4f7504fe06c9` (`qemu-scarlet`).

Observed successful scenarios include SWS readiness, the explicit
`renderer=sgfx backend=scarlet-virgl` announcement, UI rendering, mouse
increment, text entry with the matching `Input:` label, toggle changes,
interactive resize with a replacement SHM buffer, and window destruction.
The resize trace records a `1124x724` surface and `1080x680` managed geometry;
the resized UI remained interactive. These are manual integration results,
not assertions made by the QMP transport tests.

Input and resize evidence was collected before the bulk-initialization fix;
post-fix checks confirmed startup rendering, successful additional-window
creation, and eventual Showcase launcher rendering, not the entire scenario
matrix. Keep these scopes separate when comparing revisions.

The runtime test also exposed a debug-build startup problem: SWS zeroed a new
SHM buffer one byte at a time before answering window creation. In the
4-vCPU failure, a `764x764` buffer took from guest time `73.162229` to
`81.573234` to initialize, exceeding the client's 5-second response deadline.
SWS then logged `Failed to send atomic WINDOW_CREATED: Io`, and Showcase
reported `Failed to create surface`. The fix uses `core::ptr::write_bytes`
over the same writable extent; it does not skip zeroing, increase timeouts,
or change the wire protocol. Later 1-vCPU startup fills took approximately
36–539 ms, and the 4-vCPU Showcase creation completed successfully.

The subsequent user acceptance closes the current QEMU usability check; do not
keep the historical debug timing as a blocker or require the user to repeat
that confirmation. Record the final candidate image and toolchain revisions
during release rehearsal as usual. A618 hardware coverage remains a separate
item. QMP `screendump` was unsupported by this VirGL/Cocoa surface, so the
earlier visual evidence used captures of the QEMU window rather than switching
to a software GPU.

An earlier full desktop image attempt from the committed
`aarch64-limine-full` project stopped in `yt-for-scarlet`'s `yt` package,
inside its vendored `ring 0.17.14`,
at `ring-core/check.h:27`, with `fatal error: 'assert.h' file not found`.
That external vendored C build is not the root Cargo graph verified by the
focused fixture. Subsequent diagnosis traced the regression to `c99a35bb`:
the shell's `CC_aarch64_unknown_scarlet` overrode the cross GCC selected by
`yt`'s `.cargo/config.toml`. The vendored `ring` lacks the root fork's Scarlet
branch enabling `RING_CORE_NOSTDLIBINC` for Clang. Switching compilers without
that branch lost the C headers that were available with cross GCC. This was
a regression introduced by the CI workaround, not an unrelated pre-existing
failure. The follow-up uses the lower-priority `TARGET_CC` fallback instead.
The pre-existing local full-project lockfile edits were excluded from
verification and left untouched. The successful full-image rebuild is recorded
in the cross C compiler follow-up above; runtime readiness is still separate
from build success and the focused fixture.

After the SWS fix, staged-source validation passed formatting, all 7 QMP
tests, locked std/legacy integration on both architectures, 1157 RISC-V and
1128 AArch64 kernel tests, and both full build tasks. The userspace lockfile
was unchanged. Strict kernel Clippy reproduced the existing 1110-diagnostic
baseline; it is not a passing lint gate.
