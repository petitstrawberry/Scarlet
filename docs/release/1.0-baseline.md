## Toolchains and local results

The primary compiler is the `scarlet-rust-toolchain` output of
`scarlet-rust-nix` revision `2b4ddd555389a8c53806bbc2586440b2662c38dd`,
matching Scarlet's `flake.lock`. The additional portability compiler is
upstream `nightly-2025-12-31`. Host verification used macOS on AArch64;
published host CI used Linux. Compiler build directories were kept separate
for the final results.

Scarlet's Nix dev shell and Docker image select unwrapped Clang only for the
two built-in Scarlet targets (`c99a35bb`). This prevents native Linux libc
headers from leaking into C dependencies such as `ring`. Native C builds still
use the Nix wrapper; Rust userspace remains std-enabled.

The reusable Scarlet integration commands are:

```sh
cargo make check-sgfx-riscv64
cargo make check-sgfx-aarch64
```

These checks run before the ordinary build in CI so an unlocked build cannot
silently repair the userspace lockfile before it is checked. Each task now
checks all std binaries with `--bins`, including `sws`, `sgfx-cube`,
`sgfx-texture`, `sgfx-showcase`, and `ui-sgfx-showcase`, plus legacy
`sgfx-probe` and `ui-demo`. The all-binaries follow-up was checked from the
staged source tree without unrelated local changes; the published migration
CI listed above predates this expanded coverage. These checks do not boot
the applications or establish runtime compatibility.

## Diagnosed CI failures

The [AArch64 failure at Scarlet `1991dd16`](https://github.com/petitstrawberry/Scarlet/actions/runs/33891757736)
was in `test_deferred_release_migrates_ready_task`. Its fixture marked a
synthetic CPU 1 online without booting its interrupt controller. Enqueuing a
task on that CPU attempted a real reschedule IPI and panicked with
`online CPU must accept reschedule IPI: source_cpu=0 target_cpu=1`.
Commit `4f209dc3` corrects the four affected queue-policy fixtures by modeling
an already in-flight IPI. It does not change production IPI delivery or remove
the queue/migration assertions. The dedicated IPI coalescing test remains.

The later [failure at `a194f4b5`](https://github.com/petitstrawberry/Scarlet/actions/runs/33944938089)
occurred in both userspace integration steps, before the kernel tests ran.
Nix's host Clang wrapper injected Linux glibc headers into the Scarlet-target
`ring` C build, causing `_FORTIFY_SOURCE` and missing `gnu/stubs-32.h` errors.
Commit `c99a35bb` supplies target-specific unwrapped Clang. This is a C
cross-compilation environment correction, not a change from Rust std to no_std.

The [subsequent CI run](https://github.com/petitstrawberry/Scarlet/actions/runs/33945632075)
passed both kernel suites (RISC-V 1157 and AArch64 1128 tests) and all other
jobs. The suites also passed again locally while verifying the SWS manifest
follow-up. Existing Clippy diagnostics are a separate unresolved baseline,
not the cause of either failed CI run.

## Remaining release gates

- ScarletUI still filters
  `default_scroll_view_warm_scroll_allocates_zero_after_warmup` because its
  allocation budget is host-runtime sensitive. Resolve its intended guarantee
  and the ignored tests before final 1.0.
- Existing compiler and Clippy warnings need fixes or an explicit disposition.
  The root formatting task also reports a missing optional `drivers/` directory
  while exiting successfully; this is not a formatting failure.
- QEMU VirGL desktop integration and A618 hardware workloads have not been
  revalidated as part of this baseline. Cross-compilation does not establish
  presentation, input, resource-lifetime, or hardware compatibility.
- Public API/ABI contracts, release-package inventory, immutable tag staging,
  and dependency-update automation remain on the roadmap. No package version
  was bumped and no release tag was created by this migration.
