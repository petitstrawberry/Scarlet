# ScarletUI Architecture

ScarletUI is Scarlet's declarative UI framework. It is designed as a
multi-platform UI layer: the same application code declares scenes and calls
`app.run()`, while the build selects the platform implementation.

## Goals

- Keep application code independent from the platform implementation.
- Use `Application::scenes()` as the only top-level application UI entry point.
- Run each top-level window with an independent rendering pipeline.
- Keep SWS-specific behavior available for Scarlet-tightly-coupled programs
  without making ordinary applications depend on SWS.
- Support both Scarlet OS/SWS and native desktop development from the same UI
  model.

## High-Level Flow

```text
Application::scenes()
  -> Scene declarations
  -> ApplicationRunner<SelectedPlatform>
  -> WindowSlot { WindowId, SceneWindowKey, PipelineId, RenderingPipeline, PlatformWindow }
  -> PlatformWindow::present_with_damage()
```

The selected platform is compile-time feature state:

- `platform-sws`: Scarlet OS integration through SWS.
- `platform-winit`: native desktop integration through winit + softbuffer.

Application code does not pass a platform implementation to `run()` and does not branch on the
selected platform.

## Application And Scene Model

`Application` declares top-level windows through `scenes()`:

```rust
pub trait Application: Clone + 'static {
    fn scenes(&self) -> impl Scene;

    fn init(&mut self) {}
    fn on_idle(&mut self) {}
    fn on_window_created(&mut self, _ctx: &WindowContext, _window: &mut dyn PlatformWindow) {}
    fn on_window_sync(&mut self, _ctx: &WindowContext, _window: &mut dyn PlatformWindow) {}
    fn on_window_resize(&mut self, _ctx: &WindowContext, _width: u32, _height: u32) {}
    fn exit_when_all_windows_closed(&self) -> bool { true }
}
```

`body()` remains the composition hook generated by `#[derive(View)]` for normal
view components. It is not the application UI entry point.

```rust
impl Application for MyApp {
    fn scenes(&self) -> impl Scene {
        WindowGroup::new(
            "main",
            Window::new("My App", self.content())
                .app_id("org.scarlet-os.my-app")
                .size(Size::new(800.0, 600.0)),
        )
    }
}
```

`SceneBuilder` turns scenes into stable top-level `WindowDeclaration` values.
`SceneWindowKey` is declaration identity; `WindowId` is runtime identity.

## Runner

`ApplicationRunExt::run()` delegates to the selected platform module:

```rust
#[cfg(feature = "platform-sws")]
type SelectedBackend = crate::platform::SwsBackend;

#[cfg(feature = "platform-winit")]
type SelectedBackend = crate::platform::WinitBackend;
```

`ApplicationRunner<B: PlatformBackend>` is platform-neutral. Its responsibilities
are:

- collect scene declarations
- create one `WindowSlot` per opened window
- poll events from each slot's `PlatformWindow`
- dispatch events into that slot's `RenderingPipeline`
- route emitted window events to `close`, `minimize`, `maximize`, `restore`, and
  `request_move`
- remove closed slots
- call app lifecycle hooks
- present dirty pipelines

`Event::Quit` closes only the window that emitted it. Application exit is a
policy decision based on all windows being closed.

## Platform Boundary

`PlatformBackend` is the internal window factory:

```rust
pub(crate) trait PlatformBackend {
    type Window: PlatformWindow + PlatformWindowState + 'static;

    fn output_scale_milli(&mut self) -> u32;
    fn create_window(&mut self, request: WindowCreateRequest) -> Result<Self::Window>;
}
```

`PlatformWindow` is the platform-neutral interface used by the runner:

```rust
pub trait PlatformWindow: Any {
    fn poll_event(&mut self) -> Option<Event>;
    fn wait_for_event(&mut self, timeout: Duration);
    fn present(&mut self, buffer: &Buffer);
    fn present_with_damage(&mut self, buffer: &Buffer, damage: Option<&[DamageRect]>);

    fn set_title(&mut self, title: &str);
    fn size(&self) -> Size;
    fn resize(&mut self, width: u32, height: u32) -> Result<()>;

    fn close(&mut self) -> Result<()>;
    fn minimize(&mut self) -> Result<()>;
    fn maximize(&mut self) -> Result<()>;
    fn set_fullscreen(&mut self, fullscreen: bool) -> Result<()>;
    fn restore(&mut self) -> Result<()>;
    fn request_move(&mut self) -> Result<()>;

    fn sync_text_input(&mut self, state: Option<&TextInputElementState>);
    fn platform_window_id(&self) -> u64;
    fn as_any_mut(&mut self) -> &mut dyn Any;
}
```

The close contract is important: `PlatformWindow::close()` performs the platform
close operation only. It must not enqueue another `Event::Quit`; the runner
already owns slot removal.

## Platform Implementations

### SWS

`SwsBackend` creates `SWSPlatformWindow` values backed by `sws-client` and
`sws-protocol`.

SWS handles:

- surface creation and destruction
- shared-memory buffer presentation
- SWS input events
- independent maximized and fullscreen presentation states
- Scarlet window types
- menu titles and menu callbacks
- SWS text-input protocol
- SWS-specific window IDs (`surface_id`)

Fullscreen is exposed by the backend-neutral `PlatformWindow` trait. An
application can synchronize declarative state from `on_window_sync` without
depending on `SWSPlatformWindow` or a surface ID:

```rust
let _ = window.set_fullscreen(fullscreen);
```

`set_fullscreen(bool)` and `maximize()`/`restore()` are intentionally separate:
fullscreen is a desired presentation state, while maximize and restore are
window operations. SWS controls output occupancy and stacking. ScarletUI
decorations are client-side, so an application that enters fullscreen should
also render its `Window` with `.decorated(false)`. The bundled `ui-demo` does
both from its “Enter Fullscreen” button.

### Winit

`WinitBackend` creates `WinitPlatformWindow` values backed by winit and
softbuffer.

Winit handles:

- native desktop window creation
- event pumping through `pump_app_events`
- physical-to-logical coordinate conversion
- output scale / Retina scaling
- softbuffer presentation
- keyboard, character input, and IME preedit/commit mapping
- native minimize/maximize/close/move requests

The winit event loop is hidden inside the platform window. The runner still sees
only `poll_event`, `wait_for_event`, and `present_with_damage`.

## Rendering Pipeline

Each opened top-level window owns one `RenderingPipeline`.

```text
State update
  -> dirty ElementId registered under PipelineId
  -> build / reconciliation
  -> layout
  -> paint
  -> composite dirty rects
  -> present
```

Dirty state is partitioned by `PipelineId`, so one window cannot consume another
window's dirty elements.

`SceneWindowRootElement` is the per-window root. It resolves the current view for
its `SceneWindowKey` by re-evaluating `app.scenes()`, then updates only the
matching declaration's view tree.

## Window Controls

ScarletUI renders its own decorated titlebar when `Window::decorated(true)` is
used. The titlebar emits platform-neutral window events:

- `CloseRequested`
- `MinimizeRequested`
- `MaximizeRequested`
- `RestoreRequested`
- `MoveRequested`

The runner drains these emitted events and calls the current slot's
`PlatformWindow`. This keeps application code and `Window` view code independent
from SWS or winit.

## Text Input

Focused text input state is extracted from the current pipeline and synchronized
to the platform window after events and before presentation.

SWS receives and emits Scarlet text-input protocol events. Winit maps native
keyboard and IME events into the same ScarletUI event model:

- committed text becomes `TextInputCommit`
- preedit text becomes `TextInputPreedit`
- plain character input becomes `KeyEvent::Char`
- IME state is enabled only while a text input is focused

## Native Live Preview

ScarletUI preview is a development-only native desktop host. It does not change
`Application::run()` and does not expose platform selection to application code.
Preview entry points are explicit Rust functions annotated with
`#[scarlet_ui::preview]`. Multiple preview functions can live in the same crate.
The functions usually return view fragments directly; `Window` is optional and
is only needed for window-specific preview behavior. Preview names are generated
from function names by default, and `width` / `height` attributes can provide a
preferred initial preview size.
The preferred setup for binary crates is to declare `[lib] path = "src/main.rs"`
or another UI-focused source file, so the preview host can stay on the normal
library-target path. Direct source-file targeting remains as a fallback.

Stateful previews should return the state-owning view itself, not an
already-expanded fragment that has read `State::get()`. The preview host mounts
the returned view as a component shell and subscribes to its `listenables()`.

The preview host:

- builds the preview crate with the `preview` feature
- loads the generated dylib with the same Rust toolchain ABI
- exposes all registered preview functions from the dylib
- creates a normal `RenderingPipeline` for the exported view
- routes input, IME state, titlebar controls, resize, and damage presentation
  through the native platform window
- watches Rust source and Cargo files, then rebuilds and reloads the dylib after
  successful builds

Hot reload is intentionally scoped to preview sessions. Scarlet OS execution and
normal native application execution continue to use the selected platform runner.

## Feature Matrix

| Build feature | Uses std | Platform | Notes |
|---------------|----------|----------|-------|
| `std`, `platform-sws` | yes | SWS | Used by std-bin Scarlet targets. |
| `std`, `platform-winit` | yes | winit + softbuffer | Used by native desktop development. |
| `legacy-scarlet-std`, `platform-sws` | no Rust std | SWS | Uses Scarlet's legacy no_std-compatible std layer. |

`platform-sws` and `platform-winit` are mutually exclusive. `std` and
`legacy-scarlet-std` are mutually exclusive.
